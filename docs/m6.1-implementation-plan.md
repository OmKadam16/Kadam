# M6.1 — Component Compiler Integration Plan

**Status:** Implemented — Phases A–E complete.
**Scope:** Make the existing component core usable end to end in a real Kadam
project.
**Depends on:** M5 (approved) and the M6 component architecture in
`docs/components.md`.
**Does not implement:** a visual editor, a client runtime, component libraries
beyond one example, incremental compilation, or visual inspection.
Content slots, named slots, component namespaces, and the url, image, length,
and color parameter types were added after M6.1 (see `docs/components.md`
section 4.13 and `docs/component-imports.md`).

---

## 1. Goal

M6.1 is complete when a project can declare components in `kadam.json`, use
them from pages, build deterministic HTML/CSS, watch component files in
development, and expose component instance/declaration source locations.

The existing component parser, catalog, validation, interpolation, and
expansion layers already exist and are tested. The missing work is the
**product pipeline** around them.

### Current baseline

`npm run check` passes 171 tests at the Phase D checkpoint. The existing
component tests cover:

- component declarations, parameters, defaults, and variants;
- component instances and property bindings;
- catalog construction and duplicate names;
- property, variant, interpolation, cycle, depth, and element-limit checks;
- expansion to built-in kinds;
- one-pass substitution and page-owned literal braces.

Phases A–D connect that machinery to the product pipeline: pages are parsed
with validation deferred, components are catalogued and validated, pages are
expanded, validated, analyzed, and lowered, and dev builds watch component
sources. Phase E remains.

---

## 2. Non-goals and guardrails

- Keep `.kdm` as the source of truth.
- Keep the compiler deterministic and free of runtime dependencies.
- Do not add a second parser, renderer, or CSS generator.
- Do not add editor UI code or expose source maps over HTTP in M6.1.
- Do not add client-side JavaScript to production output.
- Do not add slots, imports, namespaces, or new parameter types.
- Do not add incremental compilation.
- Do not change existing page-only output. Existing projects must remain
  byte-identical.
- Do not silently skip a malformed component or page. Component errors are
  build errors.

---

## 3. Target compiler pipeline

The current pipeline is:

```text
manifest
  -> parse pages
  -> validateDocument (inside parseSource)
  -> title table
  -> analyzeDocument
  -> collect assets
  -> lowerDocument
  -> emitHtml / emitPageCss
```

M6.1 changes it to:

```text
manifest (pages + components)
  -> load manifest
  -> parse page sources without structural validation,
     allowing unresolved component kinds
  -> parse component sources
  -> build component catalog
  -> build page-title table
  -> validate component declarations and the component graph
  -> validate component instances used by pages
  -> expand each page to built-in elements
  -> validate each expanded page
  -> analyze each expanded page
  -> collect and resolve assets from expanded pages
  -> lower expanded pages
  -> emit HTML/CSS
```

The important ordering rules are:

1. Pages must be parsed with component kinds allowed; the default public
   parser behavior must continue to reject component kinds.
2. Page structural validation is deferred until after expansion. Validating the
   original page would either reject component kinds or report misleading
   required-content errors on instances.
3. Component declarations are validated even when unused.
4. Page instances are validated before expansion so missing/unknown properties
   produce one precise diagnostic rather than duplicate expansion diagnostics.
5. Expansion is all-or-nothing. No files are emitted if any page, component, or
   component instance fails.
6. Source maps retain both declaration spans and the complete instance chain.

### 3.1 Pipeline pseudocode

```ts
const manifest = loadManifest(...)
if (manifest === null || diagnostics.hasErrors) return noFiles()

const loadedPages = loadPages(manifest.pages)
if (diagnostics.hasErrors) return noFiles()

const componentFiles = loadComponents(manifest.components ?? [])
if (diagnostics.hasErrors) return noFiles()

// buildComponentCatalog() merges each ComponentFile.diagnostics and owns the
// KDM4008 "no component declaration" check. Add its diagnostics exactly once.
const { catalog, diagnostics: catalogDiagnostics } =
  buildComponentCatalog(componentFiles)
diagnostics.addAll(catalogDiagnostics)
if (diagnostics.hasErrors) return noFiles()

const titleTable = buildTitleTable(loadedPages)
if (diagnostics.hasErrors) return noFiles()

const semanticPages = ...
diagnostics.addAll(validateComponentCatalog(catalog, { pages: semanticPages }))
for (const page of loadedPages) {
  diagnostics.addAll(validatePageComponents(page.document.page, catalog, {
    pages: semanticPages,
  }))
}
if (diagnostics.hasErrors) return noFiles()

const expandedPages = []
for (const page of loadedPages) {
  const expansion = expandPage(page.document.page, catalog)
  diagnostics.addAll(expansion.diagnostics)
  if (expansion.page === null) continue

  const document = { ...page.document, page: expansion.page }
  validateDocument(document, diagnostics)
  expandedPages.push({ ...page, document })
}
if (diagnostics.hasErrors) return noFiles()

for (const page of expandedPages) {
  diagnostics.addAll(analyzeDocument(page.document, { pages: semanticPages }))
}
if (diagnostics.hasErrors) return noFiles()

collectAssetReferences(expandedPages, ...)
if (diagnostics.hasErrors) return noFiles()

lowerDocument(...)
```

`validateComponentCatalog()` already validates declarations, defaults,
interpolation, nested references, cycles, and page-title bindings. It also
merges each `ComponentFile.diagnostics` and reports `KDM4008` when a component
file contains no component declaration. `validatePageComponents()` validates
direct page instances. They must both run; neither replaces the other.

Component parser diagnostics must be stored on the `ComponentFile` and merged
only by `buildComponentCatalog()`. Do not also add them to the project’s
`DiagnosticBag` in `loadComponents()`; that would duplicate every component
syntax error.

## 4. Data model

### 4.1 Component origin metadata

Add compile-time-only origin metadata to the AST. The parser does not set it;
the expander sets it on cloned component elements.

`src/core/ast/nodes.ts`:

```ts
export interface ComponentInstanceOrigin {
  /** Component being instantiated. */
  readonly component: string;
  /** null means the default body. */
  readonly variant: string | null;
  /** Name of the instance at the call site. */
  readonly instanceName: string;
  readonly instanceSpan: Span;
  /** Declaration span of the component. */
  readonly componentSpan: Span;
  /** Span of the component name in its declaration. */
  readonly componentNameSpan: Span;
}

export interface ComponentElementOrigin {
  /** Component that owns this expanded element. */
  readonly component: string;
  readonly variant: string | null;
  /** Instance-name path from the page to this component. */
  readonly instancePath: readonly string[];
  /** Outer-to-inner instance chain, including the current instance. */
  readonly instances: readonly ComponentInstanceOrigin[];
}

export interface ElementNode extends NodeBase {
  // existing fields...
  readonly componentOrigin?: ComponentElementOrigin | undefined;
}
```

`instancePath` contains instance names only, for example:

```text
home
  pricing1                  -> ["pricing1"]
    card1                   -> nodeId home-pricing1-card1
      homeLink1             -> ["pricing1", "homeLink1"]
        link1               -> nodeId home-pricing1-homeLink1-link1
```

The local element name is appended by the lowerer, not stored in the path.
This keeps the path independent of the component’s local element names.

### 4.2 IR types

`src/compiler/ir.ts` imports the origin type from the AST and adds optional
metadata to both the rendered element and its source-map entry:

```ts
export interface IrElement {
  // existing fields...
  readonly componentOrigin?: ComponentElementOrigin | undefined;
}

export interface IrSourceMapping {
  readonly nodeId: string;
  readonly name: string;
  readonly kind: BuiltinKindName;
  readonly span: Span;
  readonly nameSpan: Span;
  readonly componentOrigin?: ComponentElementOrigin | undefined;
}
```

The source-map entry’s `span` and `nameSpan` point to the local element
declaration in the component file. The component origin chain supplies the
instance call site and all outer instances.

### 4.3 Identity rules

For a page element with no component origin:

```text
nodeId:    <page-slug>-<element-name>
className: kdm-<page-slug>-<element-name>
```

For an expanded component element:

```text
nodeId:    <page-slug>-<instance-path...>-<local-element-name>
className: kdm-c-<ComponentName>-<variant-or-default>-<local-element-name>
```

Examples:

```text
home-pricing1-card1
kdm-c-PriceCard-default-card1

home-navigation1-homeLink1-link1
kdm-c-NavLink-default-link1
```

The form input ID is derived from the element’s `nodeId`:

```text
<nodeId>-input
```

This preserves existing page-only IDs exactly and makes two instances of the
same component produce different form IDs.

## 5. File-by-file changes

### 5.1 `src/compiler/manifest.ts`

**Change:** recognize and validate the optional `components` array.

- Add `components` to `KNOWN_TOP_LEVEL_KEYS`.
- Add `readonly components: readonly string[]` to `KadamManifest`.
- Parse `components` as an optional array of project-relative `.kdm` paths.
- Normalize backslashes to `/`.
- Reject empty entries, absolute paths, drive-letter paths, NUL, traversal,
  and non-`.kdm` entries.
- Default to `[]` when omitted.
- Preserve manifest order for source loading; the catalog itself is sorted by
  component name.
- Include normalized `components` in the returned manifest.

Diagnostics:

| Code | Condition |
| --- | --- |
| `KDM4007` | `components` is not an array; an entry is not a non-empty string; an entry is absolute, contains traversal/NUL, or does not end in `.kdm` |
| `KDM4008` | Duplicate component path; component path duplicates a page path |

The component path is checked again during loading for existence, regular-file
status, output-directory containment, and symlink escape. Those checks belong
in `project.ts` because they need filesystem access.

**Do not** reject an empty `components` array. A project with no components is
valid.

### 5.2 `src/compiler/project.ts`

**Change:** load components, build the catalog, expand pages, and lower the
expanded documents.

Add:

```ts
interface LoadedComponent {
  readonly sourcePath: string;
  readonly resolvedPath: string;
  readonly source: SourceFile;
  readonly document: DocumentNode;
}

interface LoadedSource {
  readonly sourcePath: string;
  readonly resolvedPath: string;
  readonly source: SourceFile;
}
```

Recommended helpers:

```ts
function loadProjectSource(args: {
  projectRoot: string;
  realProjectRoot: string;
  outDir: string;
  sourcePath: string;
  span: Span;
  overrides: ProjectCompileOptions["sourceOverrides"];
  diagnostics: DiagnosticBag;
  code: "KDM4002" | "KDM4007";
  label: "page" | "component";
}): LoadedSource | null;
```

The helper should preserve the existing page behavior:

- resolve under `projectRoot`;
- reject paths outside the root;
- reject paths inside `outDir`;
- use `sourceOverrides` by normalized path or resolved path;
- accept an override even when the file is absent;
- otherwise require an existing regular file;
- resolve `realpath` and reject symlink escapes;
- read as UTF-8;
- return a `SourceFile`;
- push it into `ProjectCompileResult.sources` exactly once.

Page loading changes:

- Call `parseSource(source, { validate: false, allowComponentKinds: true })`.
- If parse diagnostics contain errors, keep collecting and return before
  semantic work.
- If `document.page === null` and there are no parser diagnostics, add
  `KDM4008` at the file span (“page source contains no page declaration”).
- Keep route normalization, manifest-title matching, and page order unchanged.

Component loading changes:

- Iterate `manifest.components` in manifest order.
- Use the same source helper with `KDM4007`.
- Parse with `parseComponentSource`.
- Store the parser diagnostics on the resulting `ComponentFile.diagnostics`;
  do not add them to the project bag separately.
- Do not add the “no component declaration” diagnostic in the loader;
  `buildComponentCatalog` already reports `KDM4008` for that case.
- Pass the parsed files to `buildComponentCatalog`.

Project pipeline changes:

1. Parse pages and components before project-wide validation.
2. Build the page-title table from parsed pages.
3. Build the component catalog with `buildComponentCatalog`.
4. Validate the catalog with `validateComponentCatalog(catalog, { pages:
   semanticPages })`.
5. Validate direct page instances with `validatePageComponents(page,
   catalog, { pages: semanticPages })`.
6. Return no files if any diagnostics have errors.
7. Expand each page with `expandPage`.
8. Validate each expanded document with `validateDocument` (component kinds
   should now be gone).
9. Analyze each expanded document with `analyzeDocument`.
10. Collect assets from expanded elements.
11. Lower the expanded documents; do not lower the original component-bearing
    pages.

Use expanded documents for:

- `analyzeDocument`;
- `collectAssetReferences`;
- `lowerDocument`;
- source maps and emitted output.

Keep the original parsed pages for page titles, routes, source files, and
manifest title checks.

`ProjectCompileResult.sources` must include manifest, pages, and component
sources so CLI diagnostic formatting can resolve spans in both file types.

### 5.3 `src/core/parser/parser.ts`

**Change:** make page parsing configurable without changing defaults.

Add:

```ts
export interface ParseOptions {
  /** Default true. */
  readonly validate?: boolean | undefined;
  /** Default false. */
  readonly allowComponentKinds?: boolean | undefined;
}

export function parseSource(
  source: SourceFile,
  options: ParseOptions = {},
): ParseResult;

export function parseText(
  path: string,
  text: string,
  options: ParseOptions = {},
): ParseResult;
```

Behavior:

- `parseSource(source)` and `parseText(path, text)` keep current behavior:
  validate and reject component kinds with `KDM3001`.
- `parseSource(source, { allowComponentKinds: true })` permits component kinds
  while still running structural validation.
- `parseSource(source, { validate: false, allowComponentKinds: true })` is the
  project-mode page path: parse syntax now, validate the expanded page later.
- `validateDocument` remains responsible for duplicate settings, leaf nesting,
  statement capability, and other built-in structural checks.

Do not call `validateDocument` on both the original and expanded page in
project mode. That would duplicate diagnostics for built-in elements.

### 5.4 `src/core/ast/nodes.ts`

**Change:** add `ComponentInstanceOrigin`, `ComponentElementOrigin`, and the
optional `ElementNode.componentOrigin` field described in §4.

No parser code should construct this metadata. It is added only by expansion.
The field is compile-time metadata and must not affect text spans, source
identity, or page-only AST output.

### 5.5 `src/core/components/expand.ts`

**Change:** carry instance context while cloning expanded elements.

Add a context type:

```ts
interface ExpansionScope {
  readonly component: string;
  readonly variant: string | null;
  readonly componentSpan: Span;
  readonly componentNameSpan: Span;
  readonly instancePath: readonly string[];
  readonly instances: readonly ComponentInstanceOrigin[];
}
```

Update the expansion helpers:

```ts
expandPageElement(element, state, scope: ExpansionScope | null)
expandComponentElement(element, state, bindings, scope: ExpansionScope)
expandInstance(element, state, sourceBindings, scope: ExpansionScope | null)
```

Rules:

- Page-owned built-in elements keep `componentOrigin` undefined.
- An instance creates one `ComponentInstanceOrigin` with the target component
  name, selected variant, instance name/span, component declaration span, and
  component name span.
- A nested instance extends the parent `instancePath` and `instances` chain.
- Every cloned local built-in element in a component receives:

```ts
componentOrigin: {
  component: scope.component,
  variant: scope.variant,
  instancePath: scope.instancePath,
  instances: scope.instances,
}
```

- A nested component root receives the nested scope, not the outer scope.
- Page-owned children of a page element continue through the same page scope.
- Cloning must remain immutable: no mutation of the parsed page or component
  AST.
- Preserve the existing all-or-nothing behavior: if any expansion error occurs,
  return `page: null`.
- Preserve the existing 64-level depth and 10,000-element limits.
- Do not put substituted parameter values back into source spans. The existing
  behavior of pointing substituted text at the instance binding is correct.

### 5.6 `src/compiler/lower.ts`

**Change:** derive IDs, classes, form IDs, and source-map origins from
`ElementNode.componentOrigin`.

Add a helper:

```ts
function identityFor(
  element: ElementNode,
  pageSlug: string,
): { nodeId: string; className: string };
```

Rules:

- No origin: preserve `${pageSlug}-${element.name}` and
  `kdm-${pageSlug}-${element.name}` exactly.
- With origin:

```ts
const nodeId = [pageSlug, ...origin.instancePath, element.name].join("-");
const className =
  `kdm-c-${origin.component}-${origin.variant ?? "default"}-${element.name}`;
```

- Compute the identity before calling `lowerField`.
- Change `lowerField` to accept the already-computed `nodeId` instead of
  recomputing `${slug}-${element.name}`; set `inputId` to `${nodeId}-input`.
- Copy `componentOrigin` onto `IrElement`.
- Copy `componentOrigin` into `collectSourceMap` entries.
- Keep `PageIR.sourceFile` as the page source, while component element spans
  remain in the component source file.
- Do not change page-only output.

### 5.7 `src/compiler/emit-css.ts`

**Change:** deduplicate component rules by emitted class.

Before emitting base/responsive/hover/reduced-motion rules, flatten the page
and keep the first element for each `className`:

```ts
function uniqueByClassName(elements: readonly IrElement[]): IrElement[] {
  const seen = new Set<string>();
  return elements.filter((element) => {
    if (seen.has(element.className)) return false;
    seen.add(element.className);
    return true;
  });
}
```

Use the deduplicated list for all rule loops. Source maps and HTML must still
contain every instance.

Why this is safe:

- Component instances of the same component, variant, and local element share
  authored declarations.
- Parameters are text/page values only and do not affect CSS.
- Variant names are part of the class.
- Page-only classes are unique by parser rules, so existing output is unchanged.

Do not deduplicate `PageIR.elements` itself; only CSS emission uses the unique
list.

**Expected change:** none.

`data-kdm-id`, classes, form IDs, and field label associations already come
from the IR. If a bug is found, prefer fixing the lowerer rather than adding a
component branch to the HTML emitter.

## 6. Diagnostics contract

M6.1 uses the existing codes in `src/core/diagnostics/diagnostic.ts`. No new
diagnostic code is required.

| Code | M6.1 use |
| --- | --- |
| `KDM3001` | Default parser/compiler behavior when a component kind is used without a project catalog |
| `KDM3020` | Duplicate component names in the catalog |
| `KDM3021` | Invalid component body/root/variant shape |
| `KDM3022` | Unknown component |
| `KDM3023` | Missing required component property |
| `KDM3024` | Unknown component property |
| `KDM3025` | Duplicate property binding |
| `KDM3026` | Wrong property type or missing page title |
| `KDM3027` | Unknown/malformed placeholder or wrong interpolation slot |
| `KDM3028` | Component cycle |
| `KDM3029` | Unknown/duplicate/reserved/malformed variant |
| `KDM3030` | Instance children or instance-level statements |
| `KDM3031` | Invalid parameter declaration/default |
| `KDM3032` | Expansion depth or element limit |
| `KDM4007` | Component manifest entry invalid, missing, unreadable, outside the project, inside output, or not `.kdm` |
| `KDM4008` | Duplicate component path, page/component path collision, or page/component unit mismatch |

Rules:

- Component declaration errors are reported once at the declaration, even if
  several instances use it.
- Instance binding errors point at the call site and include the declaration as
  a related location where the existing validators already do so.
- Page/component unit mismatch must not be silently skipped.
- No absolute paths may appear in diagnostics.
- The global 100-diagnostic cap and `KDM9003` summary remain in force.

## 8. Test plan

### 8.1 New integration test file: `test/components-project.test.mjs`

Use a temporary project helper similar to `test/project.test.mjs`.

Required cases:

1. **Valid component project**
   - manifest declares components and pages;
   - page instantiates a component;
   - compile returns `ok: true`;
   - HTML contains expanded text and `data-kdm-id`;
   - no component kind reaches output;
   - no `<script>` in production HTML.

2. **Component CSS is emitted once**
   - two instances of the same component on one page;
   - both instances have distinct `data-kdm-id` values;
   - the component class selector appears once in the page CSS;
   - both instances render.

3. **Variants and nested components**
   - named variant changes the class suffix and output;
   - nested `Navigation`/`NavLink` expansion produces the expected node IDs;
   - the page navigation URL is resolved by title.

4. **Unique form IDs**
   - two instances of a component containing a text field;
   - input IDs and label `for` values are unique;
   - each label points at its own input.

5. **Source map origins**
   - expanded element `span.file` points at the component file;
   - `nameSpan` points at the local declaration;
   - `componentOrigin.instances` contains the call-site name/span;
   - nested instances include the complete outer-to-inner chain.

6. **Component source override**
   - `compileProject({ sourceOverrides })` changes component output without
     writing the component file;
   - the on-disk source remains unchanged.

7. **Component asset collection**
   - an image referenced inside a component is copied to output once;
   - two instances of the component do not duplicate the asset.

8. **All-or-nothing failure**
   - missing required property, unknown variant, unknown component, or invalid
     interpolation;
   - `ok: false`, `files` empty, expected diagnostic code present.

9. **Determinism**
   - two compiles produce identical files and page IR;
   - reordering manifest component entries does not change output bytes.

10. **Manifest unit mismatch**

## 9. Acceptance criteria

M6.1 is complete only when all of the following are true:

1. A project with `components` in `kadam.json` compiles successfully.
2. Component files are parsed, catalogued, validated, and expanded.
3. No component kind or unresolved placeholder reaches `PageIR` or
   `lowerDocument()`.
4. Page-only projects produce byte-identical output.
5. Components produce deterministic output across repeated builds and manifest
   component-order changes.
6. Component instances have unique node IDs and form IDs.
7. Component CSS classes are shared across instances and emitted once per page.
8. Component elements expose declaration spans and complete instance-origin
   chains in `PageIR.sourceMap`.
9. `DevSession.watchPaths` includes component files; component edits rebuild
   correctly.
10. Missing, duplicate, malformed, and cyclic component projects fail with the
    documented codes and write no files.
11. The component example builds with zero diagnostics and no script.
12. `npm run check` passes, including all existing tests and the new M6.1
    coverage.
13. No editor application, runtime, or new dependency is introduced.

## 10. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Deferring page validation changes diagnostic ordering | Diagnostics are globally sorted by file/offset/code/message; add focused tests for exact codes, not incidental order. |
| Duplicate diagnostics from catalog + expansion | Validate catalog/page instances before expansion; return on errors; expand only valid pages. |
| Component node ID collisions | Use full instance path plus local element name; test two instances and nested instances. |
| Component CSS deduplication hides distinct rules | Class includes component, variant, and local element; parameters cannot affect CSS; test repeated instances and variants. |
| Form ID collisions | Derive input IDs from the expanded `nodeId`; test two field instances. |
| Source origins lose the call site | Store outer-to-inner instance chain in `ComponentElementOrigin`; test declaration and instance spans. |
| Component path escapes the project | Reuse lexical containment, realpath, outDir, and regular-file checks; add missing, traversal, and symlink tests. |
| Component edits are not watched | Add manifest component paths to `DevSession.watchPaths`; test CSS, reload, failure, and recovery. |
| Page/component files are silently skipped | Add explicit `KDM4008` for unit mismatches and page/component path collisions. |
| Existing output changes | Preserve no-origin identity branches and run all golden/determinism tests. |
| Scope creep into editor/runtime | Enforce the non-goals in §2; M6.1 changes only compiler/dev/doc/example surfaces. |
